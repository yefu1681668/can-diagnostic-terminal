# CAN 总线与 UDS 诊断协议设计

本文档说明本项目使用的 CAN 报文布局与 UDS 协议实现要点。

## 1. CAN ID 分配

| ID | 方向 | 用途 |
|------|------|------|
| `0x310` | ECU → 总线 | 传感器数据广播，100ms 周期 |
| `0x7DF` | 诊断仪 → 总线 | UDS 功能寻址（广播，所有 ECU 都可应答） |
| `0x7E0` | 诊断仪 → ECU | UDS 物理寻址请求 |
| `0x7E8` | ECU → 诊断仪 | UDS 响应 |

> 0x7E0/0x7E8 来自 ISO 15765-4 规定的 OBD 诊断地址（ECU 地址 0x00，响应 = 请求 + 0x08）。真实整车网络里每个 ECU 有一对独立的 0x7Ex/0x7Ey。

## 2. 0x310 数据广播帧（8 字节）

| 字节 | 含义 | 编码 |
|------|------|------|
| 0..1 | 发动机转速 | 大端，rpm |
| 2..3 | 车速 | 大端，0.1 km/h |
| 4..5 | 电瓶电压 | 大端，0.01 V |
| 6 | 状态位 | bit0=有激活故障，bit1=广播开启 |
| 7 | 计数器 | 发送端递增；接收端检测跳变 → 丢帧 |

**为什么带序号**：CAN 是无连接的，丢帧不会报错。接收端用 seq 连续性量化总线质量（网关角色实测会打印 `[GW] seq gap`）。

## 3. ISO-TP（ISO 15765-2 子集）

经典 CAN 帧数据域只有 8 字节，UDS 报文经常超长（如 0x19 读 DTC 列表），需要拆包：

```
单帧 SF:   [0x0L] [数据 L 字节] [填充 0x55...]        L <= 7
首帧 FF:   [0x1H] [长度低8位] [数据前6字节]          12 位总长
连续帧 CF: [0x2N] [数据7字节]                       N = 序号 0~F 循环
流控帧 FC: [0x30] [BS] [STmin]                      （本项目简化未实现）
```

实现要点（`isotp.c`）：

- 发送端按长度自动选 SF 或 FF+CF，帧间 2ms（模拟 STmin，防接收端缓冲溢出）
- 接收端状态机：FF 记录总长开缓冲 → CF 校验序号（不连续报错丢弃）→ 拼齐返回
- 每个通信方向一个独立重组上下文（服务端/客户端各一个，互不干扰）

## 4. UDS 服务实现

### 会话与安全模型

```
默认会话 ──0x10/03──> 扩展会话 ──0x27 解锁──> 可写参数 (0x2E)
```

- 换会话会清除解锁状态（真实 ECU 惯例，防跨会话残留权限）
- 0x2E 前置条件检查顺序：DID 合法性 → 会话 → 解锁 → 值域，每步失败返回对应 NRC

### 0x27 安全访问（教学简化）

```
诊断仪: 27 01        ->  ECU: 67 01 <seed 2B>
诊断仪: 27 02 <key>  ->  ECU: 67 02        key = seed XOR 0x5A5A
```

**简化声明**：真实产品必须用带随机挑战的非对称/对称加密算法，XOR 只用于演示握手流程。客户机端（`uds.c`）收到种子会自动算密钥回发，方便单板演示。

### DTC 格式

3 字节 DTC + 1 字节状态：

```
DTC:  C1 00 87
      ^-^ ^-^ ^
      |   |   +-- 故障类型 (87=信号无效)
      |   +------ 故障子码
      +---------- 系统 (C1=电源)
状态: bit0=testFailed  bit3=confirmedDTC，激活故障 = 0x09
```

本项目的三个演示 DTC：`0xC10087` 电压过高 / `0xC20159` 超速 / `0xC30161` 轮速信号不可信，由 `fault <n>` 命令注入，注入/清除同时写黑匣子。

## 5. CAN 驱动要点

- **波特率**：APB1 36MHz ÷ Prescaler 4 ÷ (1+15+2) = 500kbps，采样点 88.9%
- **接收**：FIFO0 消息挂起中断 → `USB_LP_CAN1_RX0_IRQHandler`（注意中容量 F103 向量名与 USB 共用）→ 32 帧软件环形缓冲
- **发送**：3 个硬件邮箱 + 50ms 超时；`AutoRetransmission=ENABLE` 保障可靠投递
- **单节点现象**：NORMAL 模式下没有第二个节点回 ACK，控制器会重发直至 bus-off——这不是 bug，是 CAN 协议的 ACK 机制（双板接线后自愈）

## 6. 三角色复用设计

同一套业务栈，用 `NODE_ROLE` 宏裁剪：

| 模块 | DEMO | ECU | GATEWAY |
|------|:----:|:---:|:-------:|
| vehicle_task（广播） | ✓ | ✓ | ✗ |
| uds_server_task（服务端） | ✓ | ✓ | ✗ |
| uds_client_task（客户端） | ✓ | ✗ | ✓ |
| gateway_monitor_task（监听+黑匣子） | ✗ | ✗ | ✓ |
| CAN 模式 | LOOPBACK | NORMAL | NORMAL |

DEMO 能成立的前提是 bxCAN 回环模式会把本机发送的帧投递回自己的接收 FIFO，于是"诊断仪栈发请求 → 服务端栈应答 → 客户端栈收响应"全部在一颗芯片内完成，走的却是真实的 CAN 控制器 + ISO-TP 全流程。
